# Common Workflow Governance (v1.0 — 4-Station Jira-Centered Workflow)

All 7 skills in the `ai-engineering-workflow` suite share this governance contract. If any older wording conflicts with this file, this governance reference takes precedence.

---

## 1. First-Principles Asset Boundary

To prevent repository bloat and review fatigue in small teams, artifacts are strictly partitioned into **Per-Feature Lifecycle Assets** (owned by Jira) and **System-Wide Living Assets** (owned by Git):

### 1.1 Per-Feature Lifecycle Assets (Jira + Temporary Active State)
- **Authoritative Permanent Asset:** The **Jira User Story** (`<JIRA-KEY>`), its **Sub-tasks** (`TASK-001..N`), linked **Bugs** (`BUG-*`), and structured Jira comments (Spec & Design, Dev Handoff & Code Review, QA Test Plan & Verification Table, Release Summary).
- **Temporary Local Scaffolding:** `.ai-workflow/active/<JIRA-KEY>.json` (gitignored).
  - Holds the structured machine-readable state during active development of `<JIRA-KEY>`.
  - Synchronized with Jira at every station via `.ai-workflow/bin/jira_sync.py` (or `<skill-dir>/scripts/jira_sync.py`).
  - **Cross-Machine Hydration & Bidirectional Jira Web UI Reconciliation:** When local `.ai-workflow/active/<JIRA-KEY>.json` is missing OR already exists in live mode, `jira_sync.py` (`status`, `pull`, and every station command via `load_active_story`) automatically reconciles with live Jira (`reconcile_story_with_jira`):
    1. Syncs newer cross-machine `ai_workflow_state` snapshots (`updated_at`), Story `summary`, `status`, and manual `assignee` changes (`story.role_owners`).
    2. Imports Sub-tasks manually added, completed, reopened, or reassigned in Jira Web UI (`source: "jira-ui"`, `last_synced_jira_status`).
    3. Imports linked `Bug` issues manually added, closed, or reopened in Jira Web UI (`fields.issuelinks`), blocking `close-story` until all Jira Bugs are resolved.
    4. **Description Drift Guard:** Detects manual edits to the Jira Story Description (`last_synced_description_hash`), auto-imports any newly added `AC-###` lines, and refuses to overwrite human edits on `sync-story` unless `--accept-remote-description` or `--force-overwrite` is passed.
    5. Always discovers newly created non-Done Stories in `project_key` via `POST /rest/api/3/search/jql` on `status` and `pull` even when `.ai-workflow/active/` already contains other Story files.
  - **Automatically deleted** when `team-release` runs `jira_sync.py close-story --key <JIRA-KEY>`, keeping the Git repository 100% free of per-feature process markdown files (`docs/requirements/`, `docs/design/`, `docs/ux/`, `docs/dev-prep/`, `docs/dev-delivery/`, `docs/review/`, `docs/qa/`, `docs/release/`, `docs/workflow/reviews/` are never created).

### 1.2 System-Wide Living Assets (Committed to Git)
Only system-wide rules, project workflow configuration, and long-lived architectural records live in the Git repository:
- `.ai-workflow/team-config.json` & `.ai-workflow/bin/jira_sync.py` — shared role/status/issue-type mapping and unified project-local CLI wrapper generated by `team-init`.
- `AGENTS.md` — concise AI agent entry guide, build/test commands, and link to `docs/shared/engineering-standards.md`.
- `docs/shared/engineering-standards.md` — canonical repository-wide engineering, security, testing, and architecture rules (extracted and deduplicated from `AGENTS.md` by `team-init`).
- `docs/shared/glossary.md` *(optional, created on demand)* — canonical domain terminology and untranslated product terms.
- `docs/shared/adr/ADR-<NNN>-<slug>.md` *(optional, created on demand)* — Architecture Decision Records for long-lived, cross-module, or hard-to-reverse technical decisions.
- `docs/manuals/<manual-name>/<manual-name>.html` *(optional, scale-aware HTML living manual maintained by `team-release`)* — standalone dark-sidebar product/API manual with isolated `./screenshots/` and `./diagrams/` subfolders per user-named manual (`<manual-name>`). Never create per-Story release markdown (`docs/release/`) or duplicate `.md`/`.pdf`/`.docx` manual files unless explicitly asked.

## 2. The 4-Station, 7-Skill Architecture & Zero-CLI Experience

| Station | Skill | Modes | Primary Responsibility | Jira & Local State Action |
|---|---|---|---|---|
| **Init** | `team-init` | — | Interactive inquiry to confirm Jira URL, Project Key, Jira account email & API token (saved to gitignored `.ai-workflow/credentials.json`), and role-to-person mappings; configure `.ai-workflow/team-config.json`, install `.ai-workflow/bin/jira_sync.py`, update `.gitignore`, and extract `docs/shared/engineering-standards.md` from `AGENTS.md` | `jira_sync.py init --inspect` / `jira_sync.py init` |
| **Router** | `team-next-step` | — | Read-only inspection of `team-config.json`, `.ai-workflow/active/<JIRA-KEY>.json` (with auto-hydration), and Jira state to recommend the exact next action | `jira_sync.py status` |
| **Station 1** | `team-spec` | `one-pass` / `draft` | Scale-aware Spec: Small/clear stories in one pass; Large/complex stories via iterative `draft` deep-dive + 6-Dimension AC Checklist | `jira_sync.py sync-story` |
| **Station 2** | `team-dev` | `plan` / `implement` | Decompose into `TASK-001..N` (`Sub-task`), implement code & tests, and check off completed tasks/bugs/review findings (Dev Fast-Track guarded to `<= 3` ACs & `low/medium` risk) | `jira_sync.py create-subtasks` / `complete-task` |
| **Station 3a** | `team-review` | — | Combined Dev Handoff & Code Review against ACs (AC-by-AC traceability), design, `engineering-standards.md`, plus QA external tool/env hints | `jira_sync.py handoff` |
| **Station 3b** | `team-qa` | `plan` / `verify` | 3-Tier QA (`automated` / `external` / `manual`) planning & verification across remembered **`jira-comment`** or **`qase`** (Qase TestOps) backend; `--all-pass` restricted to `automated` only to prevent false passes | `jira_sync.py record-qa` / `create-bug` |
| **Station 4** | `team-release` | — | Verify all gates + zero open Bugs, run scale-aware HTML Living Manual sync (`docs/manuals/<manual-name>/<manual-name>.html`), post release summary, transition Story to `Done`, delete `.ai-workflow/active/<JIRA-KEY>.json` | `jira_sync.py close-story` |

### 2.1 Zero-CLI Burden for Humans & Single-Command Entry (`$team-next-step`)
- **CLI Completely Hidden in Background:** Humans never need to memorize or manually type `jira_sync.py` flags. Users interact in plain natural language (e.g., `"幫我規劃 PROJ-101 訂單匯出"`, `"核准"`, `"繼續下一步"`), and the AI agent assembles and executes `python3 .ai-workflow/bin/jira_sync.py ...` automatically.
- **Only One Command to Remember (`$team-next-step`):** Team members do not need to memorize all 7 skill names. Invoking `$team-next-step` (or saying `"下一步"` / `"目前進度"`) at any point automatically inspects local/remote state and routes to the right station (including reporting `pending_automated_tcs`, `pending_external_tcs`, and `pending_manual_tcs` during QA verification).
- **Scale-Aware Fast-Track & Anti-False-Pass Guardrails:**
  - `complete-task` automatically detects `--commit` (from `git rev-parse --short HEAD`) and `--files` (from `git show` / `git diff`) when omitted, and supports comma-separated multi-ID completion (`--task-id TASK-001,TASK-002` or `REV-001,REV-002`).
  - **Dev Fast-Track (with Complexity Guard):** Only allowed for small stories (`len(acceptance_criteria) <= 3` AND `risk_level in ("low", "medium")`). When `tasks` is empty and `spec_status == "approved"`, running `complete-task --key <KEY> --task-id TASK-001` automatically creates `TASK-001` covering all Story ACs and marks it completed in one step. Stories with `> 3` ACs or `high`/`critical` risk are rejected by the Dev Fast-Track guard and MUST be decomposed via `create-subtasks` (`plan` mode) first.
  - **3-Tier Hybrid QA, Dual Backend (`jira-comment` / `qase`) & Anti-False-Pass (`record-qa`):** Test cases (`TC-001..N`) are classified into three execution types: `automated` (local AI-runnable unit/integration tests), `external` (requires external tools, CI/Staging, Playwright/Cypress against remote envs, Postman/Newman, JMeter, or third-party sandboxes), and `manual` (human visual/exploratory checks). On the first `$team-qa` run (when `qa_test_backend` in `team-config.json` is empty), the agent asks the user once to choose between **`jira-comment`** (full tables in Jira comments) and **`qase`** (idempotent Suite, Test Case, Test Run, and External Issue synchronization via Qase TestOps API v1, with `qase_api_token` stored exclusively in gitignored `.ai-workflow/credentials.json`), then remembers `qa_test_backend` for all subsequent `plan` and `verify` runs. Passing `--all-pass` ONLY marks `automated` test cases as `pass`; any `external` or `manual` test cases remain `not-executed` (`qa_status: "incomplete"`) until verified via `--junit-xml`, `--results-json`, or `--result TC-ID=pass`.
  - `close-story` automatically defaults `--commit` to `candidate_commit` (or Git `HEAD`) and `--version` to `v1.0.0` when omitted, and records the `qa_breakdown` (`automated`, `external`, `manual`) in the Release Summary.

## 3. 1-to-N Multi-Member Role Pools, Auto-Assignment & Smart Handoff

Small and growing teams frequently combine two patterns: **one person holding multiple roles** (e.g., PM + Tech Lead) and **one role shared by multiple people** (e.g., 2+ `developer`s or 2+ `qa` engineers). Role definitions live in `.ai-workflow/team-config.json` under `roles` (`pm`, `tech_lead`, `developer`, `reviewer`, `qa`, `release_manager`) and support `members` arrays with optional `specialty` tags (`backend`, `frontend`, `mobile`, `devops`).

1. **1-to-N Role Pool & Non-Destructive `auth` Append:**
   - Collaborators running `jira_sync.py auth --role <roles> [--specialty <tag>]` append/upsert themselves into `roles.<role>.members` by default without overwriting teammates (`--replace-role` only when replacing an outgoing member), while storing personal tokens in gitignored `.ai-workflow/credentials.json` (`member_credentials[<email>]`).
   - **End-to-End Jira Auto-Assignment:** Every station assigns Jira issues automatically via `PUT /rest/api/3/issue/{key}/assignee` (`safe_assign_issue`):
     - `sync-story --status draft` assigns the Story to `pm`; `--status approved` assigns to `developer` (`--to-assignee` optional).
     - `create-subtasks` (and Fast-Track `complete-task`) assigns **each Jira Sub-task** to its owning `developer` (`--task-assignee`, `"assignee"` in `--tasks-json`, `--assignee`, automatic `specialty` matching, or the sole `developer`).
     - `handoff` automatically selects a **peer reviewer** (`self_reviewed_with_ai: false`) from `roles.reviewer.members` who did not author the Story's tasks whenever available, and supports `--to-assignee` for multi-QA pools (`story.role_owners`).
     - `create-bug` traces `tc_id -> ac_id -> TASK-###`, assigns the newly created `Bug` issue directly to the `developer` who owned that slice, uploads any screenshots/recordings/logs (`--attach` / inherited `--tc-attach`) to the Jira `Bug` Attachments, and — when `qa_test_backend == "qase"` — synchronizes those same media attachments to Qase Test Run Results and a linked Qase Defect (resolved automatically on `complete-task`).
2. **Same-Person Consolidation & Auto-Chaining (`from_role` person == `to_role` person):**
   - When the current station owner and the next station owner resolve to the **same person** (matching `jira_account_id`, `email`, or `name`), `jira_sync.py` records `same_person: true` and `handoff_mode: "auto-consolidated"`.
   - Even when `same_person: true`, if `to_person.jira_account_id` is configured, `jira_sync.py` assigns the Jira issue to that `jira_account_id` so the issue never remains `Unassigned`, and includes an explicit `- **站點角色與負責人**：...` attribution line in the Jira comment.
   - Do **not** pause for redundant handoff approval ceremonies or send self-`@mention` notifications.
   - **Auto-Chaining:** When `same_person: true`, the AI agent should proactively chain into the next station (or offer a single one-line prompt: `"下一站同由您負責，是否直接繼續執行？"`) to eliminate multi-turn friction.
   - **Independent Review Safeguard:** For `team-review`, if `roles.reviewer.members` has a peer who did not implement the Story's tasks, route to that peer (`self_reviewed_with_ai: false`); otherwise if `independent_reviewer` is configured in `team-config.json`, route to `independent_reviewer`; if it is a solo/tiny team with no separate reviewer, perform the AI three-axis code review and record `self_reviewed_with_ai: true` transparently in the Jira review comment.
3. **Cross-Person Handoff (`from_role` person != `to_role` person):**
   - When the next station belongs to a **different person**, `jira_sync.py` executes a 3-part Jira handoff:
     1. **Transition Status:** Moves the Jira issue to the target status mapped in `team-config.json` (e.g., `In QA`, `In Progress`, `Ready for Release`).
     2. **Reassign Issue:** Updates the Jira issue assignee to the target person's `jira_account_id`.
     3. **Post `@mention` Comment:** Posts the station summary with an `@mention` of the next owner, triggering Jira's native email/push notification.

## 4. Inline "抓大放小" & Scale-Aware Spec Clarification
 
Human review bandwidth is scarce, yet large features fail when edge cases are silently skipped. Every skill must balance **"抓大放小"** with **Scale-Aware Deep-Dive**:
 
- **放小 (Auto-Default Routine Details):**
  - AI must never interrogate humans over conventional engineering, UI state, copy wording, or test-method details that have safe defaults under `docs/shared/engineering-standards.md` or existing codebase conventions.
  - Instead, AI makes the decision, applies it, and lists it in a concise **"AI 預設細節清單 (Auto-Decided Defaults)"** table so the human can review at a glance or override any item.
- **抓大 (Surface Material Decisions — Scale-Aware Dual Track):**
  - Ask the human **only** when a choice involves:
    1. Irreversible architecture, schema, or data-migration risk.
    2. Direct contradiction in product scope, business rules, or security policy.
    3. Major scope, cost, compatibility, or user-experience trade-off.
  - **Small / Clear Requirements (One-Pass Track):** Ask **at most 3 material questions** in a single round, each with a **Recommended Option (建議方案)** and 1-sentence trade-off. Once confirmed, sync directly as `--status approved`.
  - **Medium / Large or Ambiguous Requirements (Iterative `draft` Deep-Dive Track):** Never force a complex epic/story into a single-pass approval. Persist intermediate progress via `sync-story --status draft`, ask **3–5 focused business/boundary questions per round** across multiple rounds (`draft` -> `draft` -> `approved`), accumulate all confirmed `material_decisions`, and verify the **6-Dimension AC Completeness Checklist** (Happy Path, Role/AuthZ, Input Boundary/Idempotency, State Transitions/Concurrency, External Failure/Compensation, Legacy Data Compatibility) before marking `--status approved`.

## 5. Jira Sync Modes & Credentials

`scripts/jira_sync.py` uses only the Python 3 standard library and operates in two modes:

1. **Live Jira REST API v3 Mode (with Per-Role API Token Resolution):**
   - Activated automatically when Jira base URL (`JIRA_BASE_URL` or `jira_base_url` in `team-config.json` / `.ai-workflow/credentials.json`) and credentials (default `JIRA_EMAIL`/`JIRA_API_TOKEN` or per-role `role_credentials` in `.ai-workflow/credentials.json` / `JIRA_API_TOKEN_<ROLE>`) are configured (and `--offline` is not set).
   - During `team-init`, the agent asks the user to confirm each role's assigned person, email, and Jira API token (`--role-tokens-json` or `api_token` inside `--roles-json`), plus default fallback credentials (`--jira-email` / `--jira-token`). All tokens are stripped from `team-config.json` and stored exclusively in `.ai-workflow/credentials.json` (`chmod 0600`, automatically added to `.gitignore`).
   - Each station command (`sync-story` -> `pm`, `create-subtasks`/`complete-task` -> `developer`, `handoff` -> `reviewer`, `record-qa`/`create-bug` -> `qa`, `close-story` -> `release_manager`) automatically resolves that role's email and API token (sharing tokens across roles with the same email, or falling back to default credentials) so Jira comments and transitions appear under the acting role's Jira account, and includes explicit role/owner attribution in comments.
   - Syncs Stories, Sub-tasks, linked Bugs, status transitions, assignee changes, and ADF comments directly to Jira while updating `.ai-workflow/active/<JIRA-KEY>.json`.
   - **Progressive Role Claiming & `auth` Fast Path:** The founder running `team-init` only needs to configure **their own role(s)** (`init --role pm,tech_lead,developer --jira-email ... --jira-token ...`), leaving remaining roles in `unclaimed_roles`. When a collaborator clones the repository without local `.ai-workflow/credentials.json`, mutating station commands **never** silently fall back to offline mode (unless `--offline` is explicitly passed); instead, `status` reports `requires_member_auth: true` along with `claimed_roles` and `unclaimed_roles`, prompting the collaborator to choose which role(s) they own and bind their credentials via `jira_sync.py auth --role <ROLES> [--name <NAME>] --jira-email <EMAIL> --jira-token <TOKEN> [--qase-token <QASE_TOKEN>]`. `auth` verifies `/rest/api/3/myself`, populates the collaborator's `name`, `email`, and `jira_account_id` into `team-config.json` for claimed roles, and stores all tokens exclusively in gitignored `credentials.json` (`0600`).
2. **Local / Offline Mode:**
   - Activated when `jira_base_url` is empty in `team-config.json` (offline-only project) or when `--offline` is explicitly passed.
   - Updates `.ai-workflow/active/<JIRA-KEY>.json` deterministically and outputs the formatted Jira Markdown/payload so teams can work offline, in CI sandboxes, or paste directly into Jira.

**Security Rule:** Never hardcode `JIRA_API_TOKEN`, `QASE_API_TOKEN`, or secrets in `team-config.json`, code, or Git commits. Store credentials exclusively in environment variables or gitignored `.ai-workflow/credentials.json` / `.ai-workflow/.env` (`0600`).

## 6. Language & Traceability Conventions

- **Default Output Language:** Write all human-facing descriptions, acceptance criteria, task summaries, review findings, QA verification tables, and release notes in **Traditional Chinese (繁體中文)** by default, unless the user requests another language.
- **Technical Identifiers:** Preserve Jira keys (`PROJ-123`), requirement/AC IDs (`AC-001`), task IDs (`TASK-001`), test case IDs (`TC-001`), review finding IDs (`REV-001`), ADR IDs (`ADR-001`), commit SHAs, file paths, and code identifiers in standard ASCII format.
- **Evidence Integrity:** Never fabricate git commits, test execution results, or human approvals. "Test code exists" is never "test passed." Missing test evidence is recorded as `not-executed`, never `pass`.
